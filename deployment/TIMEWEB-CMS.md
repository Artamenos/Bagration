# Подготовка Timeweb к CMS

## Что можно сделать сейчас, без публикации

Изменения лежат в ветке `test`. Не запускайте workflow деплоя с `ref=test`, не меняйте ветку синхронизации Timeweb и не заменяйте `public_html` до приёмки CMS. Создание базы и подготовка файлов вне `public_html` не публикуют новую версию сайта. Docker на хостинге не нужен.

1. В панели Timeweb откройте «Базы данных» → «Создание новой базы данных». Создайте отдельную базу CMS с уникальным сложным паролем. Для базы и сайта на одном сервере хост — `localhost`, пользователь на виртуальном хостинге Timeweb совпадает с полным именем базы. Не открывайте удалённый доступ MySQL из Интернета. Пароль сохраните в менеджере паролей; не отправляйте в чат или GitHub.
2. В «Сайты» → Bagration → настройки версии и кодировки проверьте PHP 8.2 или новее. Для точного совпадения с локальными проверками можно выбрать 8.2; переход на другую поддерживаемую версию требует проверки CMS. Настройки Karate не меняйте. HTTPS должен работать без предупреждений браузера.
3. Проверьте через поддержку Timeweb или настройки PHP наличие `pdo_mysql`, `openssl`, `gd` с JPEG/PNG/WebP, `mbstring`, `fileinfo`, JSON и Argon2id. Нужны `upload_max_filesize >= 8M`, `post_max_size >= 10M`, `display_errors=Off`. Версия PHP в SSH может отличаться от версии сайта.
4. Подтвердите у Timeweb размещение сайта и базы в России. Перед дальнейшей установкой создайте резервную копию текущих файлов и баз через панель.

Официальные инструкции: [создание базы](https://timeweb.com/ru/docs/virtualnyj-hosting/perenos-sajtov-na-hosting/perenos-pri-pomoshchi-terminala/), [реквизиты подключения](https://timeweb.com/ru/docs/virtualnyj-hosting/bazy-dannyh/podklyuchenie-k-baze-dannyh/), [версия PHP сайта и консоли](https://timeweb.com/ru/docs/virtualnyj-hosting/php/izmenenie-versii-php/).

## Подготовка в SSH, вне рабочего сайта

Сначала только диагностические команды:

```sh
/opt/php82/bin/php -v
/opt/php82/bin/php -m
/opt/php82/bin/php -r 'echo defined("PASSWORD_ARGON2ID") ? "Argon2id OK\n" : "Argon2id MISSING\n";'
```

Если интерпретатора по этому пути нет, уточнить доступные версии в `/opt` и использовать соответствующий путь; не подменять его неизвестной дефолтной командой `php`.

Каталоги подготовки:

```sh
mkdir -p "$HOME/Bagration/shared/content" "$HOME/Bagration/shared/media" "$HOME/Bagration/releases/cms-setup/admin"
chmod 700 "$HOME/Bagration/shared"
chmod 755 "$HOME/Bagration/shared/content" "$HOME/Bagration/shared/media"
```

По SFTP загрузить содержимое локальной папки `cms` в `$HOME/Bagration/releases/cms-setup/admin/`. Эти файлы не находятся в `public_html`, поэтому не меняют действующий сайт. Такая глубина каталогов нужна текущему CMS runtime для поиска `Bagration/shared`.

Только если `shared/config.php` ещё не существует, скопировать шаблон:

```sh
test ! -e "$HOME/Bagration/shared/config.php" && cp "$HOME/Bagration/releases/cms-setup/admin/config.example.php" "$HOME/Bagration/shared/config.php"
chmod 600 "$HOME/Bagration/shared/config.php"
/opt/php82/bin/php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
```

В редакторе Timeweb заполнить `shared/config.php`: DSN с настоящим именем базы, пользователя, пароль и сгенерированный 64-символьный ключ. `origin` оставить `https://sc-bagration.ru`. Ключ нужен для защиты TOTP-секретов; сохранить его резервную копию вместе с конфигурацией. Не перезаписывать существующую конфигурацию/ключ.

Проверки и установка в пустую выделенную базу:

```sh
/opt/php82/bin/php "$HOME/Bagration/releases/cms-setup/admin/cli.php" check
/opt/php82/bin/php "$HOME/Bagration/releases/cms-setup/admin/test.php"
/opt/php82/bin/php "$HOME/Bagration/releases/cms-setup/admin/cli.php" install
/opt/php82/bin/php "$HOME/Bagration/releases/cms-setup/admin/cli.php" add-admin admin-01
```

Пароль администратора вводится скрыто, минимум 16 символов. TOTP-секрет добавить в приложение-аутентификатор: SHA1, 6 цифр, шаг 30 секунд. Каждый администратор получает отдельный аккаунт. Тестовые пароль и секрет из Docker не использовать.

На этом подготовка завершена. Старый сайт продолжает работать, новая админка ещё не опубликована. Для уже существующей непустой базы не выполнять установку вслепую — сначала проверить схему и резервную копию.

## Что сделать позже, перед включением CMS

- Закончить серверные проверки: загрузка изображений, права PHP на shared, CSRF, блокировка входа, конкурентное редактирование, удаление/восстановление и восстановление резервной копии. Проверить PHP Apache/CGI отдельно от PHP CLI.
- Принять решение о переносе контента. Git хранит код и начальный `cms/seed.json`, но не локальную базу и загруженные `/media/`. Добавленный через Docker постер и изменения дат сами с коммитом на сервер не попадут. Для их переноса нужны отдельно выбранные записи контента и файлы; локальные администраторы, пароли, ключи и тестовые журналы не переносятся.
- Перед релизом обновить серверный `timeweb-sync-production.sh` версией с поддержкой shared, сохранив предыдущую копию. Одного обновления файла в Git недостаточно: исполняемый скрипт находится вне веб-релиза.
- Только после отдельного решения о публикации собрать принятую версию и обновить `production`. Серверный скрипт должен подключить `shared/media` и `shared/content` к релизу. В `shared/content/current.json` к этому моменту должен существовать корректный опубликованный контент.
- Проверить `/admin/`, `/content/current.json`, изображения и календарь на домене; служебные файлы должны возвращать 403. Повторная доставка релиза должна сохранять контент и медиа.

## Что может выполнить агент

При предоставленном подключении к Timeweb можно выполнить серверную диагностику, подготовить каталоги, загрузить код подготовки, проверить PHP, установить схему и проверить результат. Установка и включение на рабочем домене — отдельный этап; эта инструкция сама его не запускает. Доступ к GitHub или локальному Docker не предоставляет доступ к Timeweb. Пароли не нужно публиковать в переписке; предпочтителен разрешённый SSH-доступ по ключу, а секреты можно заполнить самостоятельно в панели.
